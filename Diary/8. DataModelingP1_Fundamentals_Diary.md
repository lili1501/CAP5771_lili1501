## Which models did I choose to try first, and why?

### Problem Type
This is a **binary classification** problem — predict whether a patient will die during their ICU stay (1) or survive (0) based on clinical data from the first 72 hours.

### Models Chosen

#### 1. HistGradientBoostingClassifier (HGB)
**Why:**
- Natively handles missing values without requiring imputation — critical for medical data where many labs are missing
- Fast training on large tabular datasets (~47,000 rows)
- `class_weight='balanced'` parameter directly addresses class imbalance (~12% mortality)
- Gradient boosting generally outperforms simpler models on clinical tabular data
- Low interpretability cost compared to deep learning while still achieving high performance

#### 2. Random Forest (RF)
**Why:**
- Robust to outliers — ICU data frequently contains extreme physiological values
- Built-in feature importance via permutation importance
- Ensemble of decision trees reduces variance
- `class_weight` hyperparameter allows explicit control over minority class emphasis
- Provides good diversity from HGB for ensemble combination

#### 3. XGBoost
**Why:**
- State-of-the-art performance on tabular medical data
- `scale_pos_weight = neg/pos` directly handles class imbalance at the algorithm level
- Regularisation (L1/L2) reduces overfitting
- Complements HGB in the final ensemble — both are gradient boosters but use different implementations

#### Why not Logistic Regression?
Logistic regression assumes linearity between features and log-odds of the outcome. ICU mortality risk is driven by complex, non-linear interactions (e.g., high lactate combined with low MAP is far more dangerous than either alone). A linear model would miss these interactions.

#### Why not SVM or Neural Networks?
SVM requires scaling and is computationally expensive on 47,000+ samples. Neural networks require much larger datasets and offer limited interpretability — unacceptable for clinical decision support where clinicians need to trust and understand the predictions.

## What assumptions does my model make about the data?

### HistGradientBoosting
- Features are informative — random noise features are handled by regularisation but not eliminated
- The training distribution represents the deployment distribution (i.e., future patients resemble past patients in MIMIC-IV)
- Missing data is missing at random (MAR) — HGB handles missingness but assumes it is not systematically related to the outcome in an unmodelled way

### Random Forest
- Features are independent enough that bootstrap sampling and random feature selection produce diverse trees
- The minority class (deaths) can be oversampled via SMOTE without introducing unrealistic synthetic patients

### XGBoost
- `scale_pos_weight` correctly represents the class ratio in the deployment setting
- Sequential residual fitting will converge to a useful solution given the feature set

### All models
- The 72-hour feature window is sufficient to capture the clinical trajectory that determines ICU mortality
- Aggregation (min/mean/max) preserves enough information from the raw time-series data
- MIMIC-IV patients from Beth Israel Deaconess Medical Center are representative of the target population

## What split did I decide on for train/validation/test, and why?

### Split Used
```
Train:        80% of data (37,832 patients)
Test:         20% of data (9,459 patients)
Calibration:  15% of train set (held out from train for Platt scaling)
```

### Why 80/20?
The dataset has 47,291 patients. A 20% test set gives approximately 9,459 patients — large enough to produce stable evaluation metrics, especially for the minority class (deaths ~1,136 cases in test set). A larger test set was not needed given the dataset size.

### Why stratified splitting?
The outcome is imbalanced (~12% mortality). Unstratified splitting could result in test sets with as low as 8% or as high as 16% mortality by chance, making evaluation metrics unreliable. `stratify=y` ensures both train and test sets reflect the true 12% mortality rate.

### Why a separate calibration split?
Platt scaling (sigmoid calibration) requires a held-out set that the ensemble never saw during fitting. Using the full test set for calibration would cause data leakage — the calibrated probabilities would be overly optimistic on the test set. Holding out 15% of the training set specifically for calibration ensures honest probability estimates.

### Why no separate validation set for hyperparameter tuning?
Instead of a fixed validation set, I used **5-fold Stratified Cross-Validation** (StratifiedKFold, k=5) within `RandomizedSearchCV`. This is more efficient — each training sample is used for both training and validation across different folds, reducing the risk of overfitting to a particular validation split. The test set remains completely held out and is only used for final evaluation.

```
Random state: 42 (reproducible splits)
Stratification: yes (preserves class balance)
CV folds: 5 (within training set only)
```
