## What are the top data problems I decided to fix first, and why?

### 1. Defining the 72-Hour Time Window (Priority 1)
The most critical data problem was ensuring all clinical measurements were strictly restricted to the first 72 hours of ICU admission. This was the foundation of the entire project — including any measurements outside this window would constitute data leakage, making the model appear more accurate than it would be in real clinical use.

I addressed this first because every downstream feature depends on it. If the window was wrong, all features would be invalid.

**Rule applied:** Filter (time-based constraint)  
I created three SQL views — `chartevents_72h`, `labevents_72h`, and `outputevents_72h` — each restricting records to `intime` to `intime + 72 hours` using datetime comparison.

### 2. Dataset Sampling for Feasibility (Priority 2)
The full MIMIC-IV dataset contains over 300,000 patients. Loading it entirely into SQLite on a local machine was not feasible. I took a 50% random sample of subjects to make processing tractable while preserving statistical representativeness.

**Rule applied:** Random sampling (50% of subjects)  
```sql
SELECT subject_id FROM patients
ORDER BY RANDOM()
LIMIT (SELECT CAST(COUNT(DISTINCT subject_id) * 0.5 AS INT) FROM patients);
```

### 3. Item ID Mapping for Clinical Features (Priority 3)
MIMIC-IV stores clinical measurements using numeric item IDs (`itemid`). Before extracting any feature, I had to identify the correct item IDs for each vital sign and lab test from the `d_items` and `d_labitems` tables. Without this, feature extraction would be incorrect.

**Rule applied:** Lookup and mapping  
I queried `d_items` and `d_labitems` using label matching (e.g., `LOWER(label) = 'heart rate'`) and saved the mappings to CSV files in `Itemids/` for reproducibility.

### 4. Aggregating Raw Events to Stay-Level Features (Priority 4)
Raw chartevents and labevents contain one row per measurement. The model requires one row per ICU stay. I aggregated using `MIN`, `MAX`, and `AVG` per feature per `stay_id`, computed within the 72-hour window.

**Rule applied:** Aggregation (GROUP BY stay_id)  
Created `vital_features_72h`, `lab_features_72h`, `urine_features_72h`, and `demo_features` tables, then joined into `icu_features`.

## Before vs After Summary

**Before aggregation:**
- `chartevents` table: millions of rows, one per measurement
- `labevents` table: millions of rows, one per lab result
- No stay-level representation

**After aggregation:**
- `icu_features` table: one row per ICU stay
- Features: max/min/mean for each vital and lab within 72h
- Shape: 47,291 rows × 56 columns (after wrangling)

```
Before: chartevents → ~millions of rows
After:  icu_features → 47,291 rows × 56 columns
```

**Missingness after aggregation:**
- Lab features had higher missingness (~30–60%) than vitals (~5–15%)
- This is expected — not all patients have every lab drawn in the first 72h
- Labs like bilirubin and lactate were missing most frequently

## What risks remain?

### Sampling Bias
Using 50% random sampling may under-represent rare ICU presentations or specific demographic groups. If the 50% sample differs systematically from the full population, the model may not generalise to all patient types.

### Aggregation Information Loss
Using MIN/MAX/AVG collapses the temporal trajectory of a patient's condition into three numbers. A patient whose HR deteriorated from 80 to 140 over 72h would have the same mean HR as a patient who was stable at 110. Trend information is lost.

### Missing Lab Data
Up to 60% missingness in some lab features means the model heavily relies on imputation during training. If labs are missing in a non-random way (e.g., sicker patients get more labs drawn), imputing with the population median may introduce bias.

### Duplicate Item IDs
Multiple `itemid` values can map to the same clinical concept (e.g., both invasive and non-invasive blood pressure). Combining them under a single feature assumes they are clinically equivalent, which may not always be true.

### Fairness Concerns
Race is included as a feature. While it captures real demographic patterns in the MIMIC-IV data, using race as a predictive feature may encode systemic healthcare disparities rather than true physiological differences. This could lead to differential model performance across racial groups.
